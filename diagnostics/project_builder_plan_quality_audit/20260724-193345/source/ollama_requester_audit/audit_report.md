# Ollama-ProjectBuilder Request Boundary Audit

Date: 2026-07-24
Branch: system/full-health-audit
Scope: direct Ollama calls and isolated OllamaPlanRequester only.

No MissionState, MissionExecutor, build_project, materialization, npm, preview,
persistence or WP2 was executed. No production file, .env, model, context,
protocol, validator or AirLLM file was changed.

## 1. Executive summary

Decision:

BOUNDARY_HEALTHY_WP1_RETRY_AUTHORIZED

The direct runtime, streaming transport and requester parser all produced the
same useful response for the captured real planning payload. The previous
PLAN_READ_TIMEOUT was not reproduced, including after an explicit cold model
unload. The cold faithful payload completed in 53.63 s, with first content at
16.666 s and a maximum observed chunk interval of 0.213 s.

The remaining isolated finding is a contract distinction: the internal
ProjectBuilder plan description is not a standard JSON Schema. Sending it as
Ollama format produces HTTP 400. The JSON Schema actually used by the focal
correction requester, generated by _focal_correction_response_schema, passes.

Confidence:

- A/runtime and HTTP boundary: high;
- B/prompt evaluation without schema: high;
- D/real payload cold and warm: high;
- requester parser parity: high;
- exact cause of the historical 300-second timeout: medium, not conclusively
  identified because the old process did not preserve a raw stream and the
  present cold reproduction is healthy.

## 4. Instrumentation

probe_ollama_stream.py uses httpx directly against Ollama. It saves the exact
payload, raw response bytes, every raw NDJSON line, base64 of each raw line,
monotonic event offsets, selected response headers and parsed metrics. It does
not depend on ProjectBuilder execution.

Recorded events include call start, headers, first byte, first HTTP chunk, first
valid JSON object, first content, parse errors, HTTP errors, stream closure and
done.

The resource monitor was active for C-focal and D-cold. A1, A2, B1, B2 and warm
requester probes ran before the monitor hook was attached; their initial/final
environment snapshots and Ollama generation metrics are preserved, but they do
not have a per-test resource timeline. The memory counter through CIM was
denied, while GPU, Ollama process, CPU/GPU distribution and Ollama timing
metrics were available.

## 7. Test C - schema isolation

### C1: internal plan description sent as Ollama format

This request returned HTTP 400 in 1.370 s, before any body chunk. Ollama
reported conversion failures for the internal types array[string],
array[object] and object[array[string]]. These are ProjectBuilder internal
schema vocabulary, not JSON Schema Draft 2020-12.

This is not a failure of the actual first planning call, because that call sends
format=json and embeds the plan contract in the prompt.

### C-focal: actual focal correction schema

The schema generated by _focal_correction_response_schema was sent as structured
output with a minimal correction prompt:

- HTTP 200;
- 31 chunks;
- first content 1.639 s;
- 4,160 bytes;
- done=true, done_reason=stop;
- prompt_eval_count=170, eval_count=40.

The actual structured-output path used by the requester is therefore healthy.
C2 for the invalid internal schema was not run because C1 rejected it
synchronously; the focal standard schema probe is the relevant constrained path.

## 11. Tokenization and capacity

The exact D response reports 597 evaluated prompt tokens, well below context
8192. The output stopped at 848 tokens despite num_predict=16384; no context
overflow, truncation error or server rejection was observed. The 16,384 output
cap is not itself evidence of a timeout in this run.

## 12. Timeout semantics

The requester creates httpx.Timeout(connect=5, read=300, write=15, pool=5).
In httpcore, the read timeout is passed to each socket read while receiving
headers/body; it is not a separate total-generation timeout. The ProjectBuilder
consumes the stream with response.aiter_lines() and has no first-token,
idle-progress or total-generation timeout distinct from httpx read timeout.

The historical partial_response=false means the requester had not parsed any
content when its read timeout was raised. In the current D runs, direct stream
gaps were 0.146 s warm and 0.213 s cold, so the 300-second inactivity limit was
never approached. The built-in retry after PLAN_READ_TIMEOUT is not an exact
byte-for-byte repeat: attempt two uses compact messages, although it preserves
the same model, context and generation options.

## 14. Cause boundary

The present boundary is healthy. The previous 300-second timeout cannot be
attributed to the stream parser, HTTP buffering, prompt size, first-call JSON
mode, token-context capacity or a persistent cold load limitation. The exact
historical cause remains not demonstrated; plausible causes include a transient
Ollama/model stall or an environment state not reproduced by the controlled cold
reset. The old journal did not preserve raw stream bytes, so it cannot identify
which lower-level state existed then.

There is a separate contract defect: the internal plan schema vocabulary cannot
be passed directly to Ollama as JSON Schema. The actual focal schema generator
already produces a compatible constrained schema in the tested case.

## 15. Recommended correction

Do not change production code as part of this audit. The single follow-up
correction worth considering is a schema-boundary test that forbids passing the
internal ProjectBuilder schema document as Ollama format, and verifies every
structured-output call uses a Draft 2020-12-compatible schema such as the focal
correction schema.

Potential future files: agents/orchestrator/project_builder.py and focused
Ollama/focal-schema tests. Risk: low to medium; the test must preserve the first
call format=json and must not weaken local semantic validation.

Separately, a future timeout-policy change should only be considered after a
raw-stream capture of the original failure. It should separate first-byte,
idle-progress and total-generation limits rather than blindly increasing 300 s.

## 16. Next authorized test

Exactly one next diagnostic is authorized before a new WP1:

Repeat the exact D-cold probe once from a fresh Ollama process/runtime state,
with resource sampling active from request start through done, and compare its
first-byte, first-content, load_duration and maximum chunk gap with D-cold.

It must remain direct Ollama only. No MissionState, materialization, preview,
npm, WP1 or WP2 should be added to that test.

## 17. Final decision

BOUNDARY_HEALTHY_WP1_RETRY_AUTHORIZED

The authorization is limited: the request boundary has direct evidence of
progress and requester parity. It is not a claim that semantic plan validation
or materialization will pass, and it does not authorize WP2. A new WP1 should
only be run after the exact historical timeout question is either reproduced
with raw evidence or explicitly accepted as a transient, unreproduced event.
